## 4. 事故与修复：CLI 误报 `EPERM rename`（业务已成功）

现象：TTY 人类挑战通过后，CLI 返回错误 JSON：

```json
{"code":"DEPENDENCY_UNAVAILABLE","message":"EPERM: operation not permitted, rename '[path]' -> '[path]'"}
```

但账本与平台证据显示**业务已完整成功**（task succeeded、operation confirmed、三条回信 sent、平台评论存在）。`state.requests` 中该 `approval.decide` 请求记录了：

```text
EPERM: operation not permitted, rename 'C:\Users\22338\.dsh\dsh-bili-unified\.state.json.3680.XXXX.tmp' -> 'C:\Users\22338\.dsh\dsh-bili-unified\state.json'
```

根因：
- Windows 不允许 `MoveFileEx(REPLACE_EXISTING)` 覆盖**正被其他进程打开**的 `state.json`；
- 该轮 DSH 插件运行时（IM bridge/outbox pump + maintenance）与独立 CLI 进程同时读/写同一数据目录，CLI 的最终记账事务在 rename 时撞上读者，抛 `EPERM`；
- 业务副作用事务此前已提交，因此错误只发生在**后续记账事务**中，表现为“假失败”。

修复（本轮已提交）：
- `src/utils.js` 新增 `renameWithRetry()`：对 `EPERM/EBUSY/EACCES/ENOTEMPTY` 做有界指数退避重试（6 次，10–160ms + 抖动）；
- `atomicWriteFile`、store 锁陈旧重命名、备份索引锁陈旧重命名、备份 staging→final 目录重命名均改用它；
- 新增回归测试 `test/durable-write.test.js`：注入 transient EPERM 验证重试成功；持续失败验证抛出原错误、旧文件保留、临时文件清理。
- 本次修复后 `node scripts/check.mjs` 112 文件通过，全量测试通过（见提交记录）。

数据处理：
