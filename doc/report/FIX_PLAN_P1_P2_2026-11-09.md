## 1. 接口契约（v1，必须按此实现）

### I1 凭据写门禁（fix-core 提供，fix-gateway/fix-entry 消费）
- `CredentialService.assertWriteAllowed(state)`：无 `activeAccountRef`→`CREDENTIAL_MISSING`；账号记录缺失→`IDENTITY_UNVERIFIED`；无 sessdata→`CREDENTIAL_MISSING`；`account.credentialRevision !== credentialRevision(当前凭据)` 或无 `lastVerifiedAt`→`IDENTITY_UNVERIFIED`（信息提示先 `account verify`）；返回 true。
- `CredentialService.describeBinding(state)`：只读，返回 `{bound, accountId, credentialRevision, verifiedAt, mismatch}`，供 status/CLI 使用。
- 新状态字段（store.js 校验需放行）：`accounts[<platform:accountId>].credentialMismatchAt?`（时间戳）。
- fix-gateway：`EffectGateway` 构造新增可选 `credentials`；平台写 `reserveOperation` 与 `_prepareDispatch` 事务内调用 `this.credentials?.assertWriteAllowed(draft)`；Operation 记录 `credentialRevision`。
- fix-entry：`createRuntime` 构造 EffectGateway 时传入 `credentials`。

### I2 配置更新协议与动态生效（fix-core 主实现，fix-entry 消费）
- `ConfigService.update(patch, {source, expectedRevision})` 协议：
  1. 校验 merged、计算 hash；写 `<configFile>.next`（原子写）；
  2. `store.transaction`：事务内复核 `expectedRevision`（HTTP/命令通道必传）、migration.phase/recovery.phase/instance.status；写 `draft.configIntent = {phase:'prepared', nextVersion, nextSha256, nextFile, prevSha256, at}` + 事件 `config.update.prepared`；
  3. 原子 rename `.next` → 配置文件；
  4. `store.transaction`：`draft.configRevision = {version:nextVersion, sha256, updatedAt, timeZone}`；删除 `configIntent`；追加 `config.updated`；返回 redacted。
  5. 任一步失败：清理 intent + `.next`，revision 不变，抛错。
- 启动 `reconcileConfigIntent()`：若 intent 存在且 `.next` 存在→完成 rename 后按 3/4 提交；若 intent 存在且文件 hash 已等于 nextSha256→直接提交 revision；否则清理 intent 并告警事件。
- 新状态字段：`configIntent`（可为 null）。
- `ConfigService.onChange(fn)`：返回取消函数；成功提交后按注册顺序调用 `fn({config, previous, revision})`。
- `assertCurrentState(state)` 同时核对 `sha256` 与 `version`。
- `AgentClient.reconfigure(config)`（fix-core）；`BilibiliClient.reconfigure(config)`（fix-gateway）；fix-entry 在 `onChange` 中重启 coordinator timer、刷新 agent/client、按启用状态 start/stop maintenance。
- 新配置字段（fix-core）：`browse.failureCooldownMinutes`（0–10080，默认 360，0=不冷却）、`browse.allowNoSubtitle`（布尔，默认 false，允许无字幕时以标题/简介继续）。`config.example.json` 同步更新。

### I3 Task 修订与结算（fix-core；fix-modules 消费）
- `TaskManager.reviseInput(tx, taskOrId, {input, inputHash}, {actor})`：修订输入、`revision += 1`、`inputHash` 更新、旧未决审批置 `supersededAt`、追加 `task.input.revised` 事件、重算结算。
- `TaskManager.resume` 成功后 `revision += 1` 并清 `finishedAt`。
- `pendingApprovals` 统计排除 `supersededAt` 的审批。
- `recompute`：维护 `hasUnknownOperation`（由 pendingOperationIds 指向的 Operation 中是否存在 unknown/dispatching 计算）；`succeeded` 的 `isSettled` 也计入 pendingApprovals；`running` 清 `finishedAt`。
- `validateState` 对每个 task 调用组合校验（`assertSettledCombination` 等价逻辑），非法组合抛 `STORE_CORRUPTED`。
- `assertTransition` 中 `provenUndispatched` 等布尔由 TaskManager 自行核对：检查 `tx.state.operations` 是否存在该 task 关联且带 `dispatchAt` 的 Operation，存在则拒绝 cancelled。

### I4 ExecutionDispatchContext（fix-gateway 签发，fix-prodmig/fix-entry 消费）
- `contracts.js` 新增纯函数 `createExecutionDispatchContext({executionId,taskId,stageId,attempt,inputHash,instanceId,profileId})` → `{executionId,taskId,stageId,attempt,inputHash,instanceId,profileId,permit:'dispatch-once',issuedAt:ISO}`；`assertExecutionDispatchContext(context)` 保持形状校验。
- `EffectGateway.issueExecutionContext(record)`：生成随机 token 并按 token 记录 `{executionId,taskId,stageId,attempt,inputHash}`，返回上下文（含 `token`）。
- `EffectGateway.executionContextVerifier`：`{verify(context), consume(context)}`，token 未签发/字段不匹配→`FORBIDDEN`。
- fix-prodmig：`_dispatchStage` 在持久化 execution 的同一事务后调用 `effectGateway.issueExecutionContext`，把上下文作为 `stageRequest.dispatchContext` 传给 backend；`LocalExecutionBackend` 构造新增可选 `executionContextVerifier`，提供时 `submit` 必须先 `verify` 上下文（缺失/伪造→`FORBIDDEN`），并 `consume`。
- fix-entry：`getBackend()` 构造时传入 `executionContextVerifier: effectGateway.executionContextVerifier`；构造顺序需保证 gateway 先于 backend 使用（用延迟 getter）。

### I5 迁移封存后晚到回执（fix-prodmig 提供，fix-gateway 调用，fix-entry 注入）
- `MigrationService.noteLateLedgerWrite(draft, tx, {operationId, kind})`：当 `draft.migration.phase === 'sealed'` 时把 phase 改回 `'quiescing'`，向 `draft.migration.lateReceipts` 追加 `{operationId, kind, at}`，作废封存包（`draft.migration.sealedPackage = null` 或等价字段），追加 `migration.sealed.reopened` 事件；返回 true。非 sealed 返回 false。
- `EffectGateway` 构造新增可选 `services`；`_settleDispatch` 与 `resolve` 写入 Operation 最终状态的同一事务内调用 `this.services?.migration?.noteLateLedgerWrite?.(draft, tx, {...})`。
- fix-entry：构造 EffectGateway 时传 `services: { get migration(){...}, get diary(){...} }`（延迟 getter，因 migration 在 gateway 之后创建）。
- release 回执的 `cutEventSeq/sourceHistoryEpoch/snapshotHash` 必须取自 sealed manifest，不得取 release 时刻的 state。

### I6 resolve 后日记待重建（fix-gateway 调用，fix-modules 实现）
- `DiaryModule.markDirty(draft, tx, {kind, accountRef, taskId, operationId, date})`：向 `draft.diaries` 的待重建索引写标记（建议 `draft.diaries.__pendingRebuild = { '<diaryId>': {date, scope, reason, at} }`；`__pendingRebuild` 为保留 key，正常 diaryId 不会同名），追加 `diary.rebuild.marked` 事件；不生成文件、不调模型。
- `EffectGateway.resolve` 成功后（同事务）调用 `this.services?.diary?.markDirty?.(...)`。
- fix-modules：`DiaryModule.generate` 启动时读取并消费 `__pendingRebuild` 中匹配 date/scope 的标记；`force=true` 强制重建；叙述生成移到日记身份锁外，先比对事实 hash 再决定是否调模型；恢复来源/缺口标注（`recoveryDerived` 与父恢复点信息）写入正文；每日定时与 afterBrowse 都经 `runDiary` 走 `_exclusive('diary')`；两个 book 分别生成；仅成功后推进 `diaryLastDate`，失败不推进。

### I7 DM 冷却事务内检查（fix-gateway 支持，fix-modules 使用）
- `EffectGateway.reserveOperation(data)` 支持可选 `data.cooldown = {businessKey, days}`：事务内检查 `draft.businessKeys[businessKey]` 的最近确认/更新时刻，冷却期内→`DUPLICATE_TARGET`。
- fix-modules：`direct-messages` 把 `sameVideoDays` 冷却改为通过 `cooldown` 传入预留事务（模块内不再用事务外快照判断）。

### I8 发布元数据能力（fix-gateway 提供，fix-modules 调用）
- `BilibiliPlatformAdapter.capabilities.publish.manual` 增加 `limits: {titleMaxBytes:80, descriptionMaxBytes:2000, tagsMax:12, tagLengthMax:20, tidRequired:true}`；新增 `async validatePublishMetadata(metadata)`，不合规抛 `PUBLISH_INPUT_INVALID`（含字段名）。
- fix-modules：`publisher` 优先调用 `adapter.validatePublishMetadata`，适配器未提供时回退现有硬编码校验。

### I9 新增受信本地命令（各 owner 提供模块方法，fix-entry 接线）
- `EffectGateway.cancelOperation({operationId, reason, evidence}, humanContext)`：仅允许 `reserved` 且无 `dispatchAt` 的 Operation，释放额度/业务键占用、状态转 `cancelled`、追加事件；已派发/unknown→`FORBIDDEN`。→ 命令 `operation.cancel`，CLI `operation cancel <id> --reason <text> --confirm`。
- `PublisherModule.markNotPublished({taskId, reason, note}, humanContext)`：仅 Manual 且无已派发/unknown Operation 的 `awaiting_manual` Task；同事务更新 Publish/Task/事件，保留 Bundle；→ 命令 `publish.void`，CLI `publish void <task-id> --reason <text> --confirm`。
- `MigrationService.releaseTaskHold({holdId, taskId, note}, humanContext)`（fix-prodmig）：释放 `kind==='migration'` 的 task hold（写 `releasedAt/releaseDecisionRef`、审计事件、重算 task）；→ 命令 `migration.release-hold`，CLI `migration release-hold <hold-id> --task <task-id> --note <note> --confirm`。
- `CredentialService`/`RateLimiter` 提供 `clearAuthPause(state/tx, accountKey, evidence)`（fix-gateway 在 rate-limiter 实现）；→ 命令 `account.resume`，CLI `account resume --platform bilibili --note <note> --confirm`。
- `RecoveryService.preserveCorruptSource({dataDir, note}, humanContext)`（fix-prodmig）：把损坏/待恢复现场的 state/journal/instance 复制到 `<recoveryDir>/corrupt-<timestamp>/` 并写 manifest hash；→ 命令 `recovery.preserve`，CLI `recovery preserve --data-dir <dir> --note <note> --confirm`。
- fix-entry：`OWNER_ONLY_ACTIONS`、命令白名单、HTTP 不开放这些管理动作（仅 CLI），并保证人类证明。

## 3. 协作规则
1. 开始前先读本文件、`doc/report/IMPLEMENTATION_AUDIT_2026-11-09_POSTFIX.md` 对应章节与你范围的分域报告。
2. 每完成一个 item：跑该 item 相关测试文件 + 你名下的全部测试文件，全绿再标记完成。
3. 需要他人文件改动：`send_message` 给 lead，写明文件、位置、期望行为；不要自行编辑。
4. 发现契约冲突或设计歧义：先按契约实现最保守版本，并在回报中说明；不要扩范围。
5. 新增测试统一放各自 `test/fix-*.test.js`，不要删改既有测试断言（除非行为按设计变更且在新测试中说明）。
6. 回报给 lead：完成项清单（含 file:line）、未完成/受阻项及原因、运行过的测试命令与结果、需要 Lead 处理的跨文件事项。
7. 不要运行 `npm test`/`npm run check`/`npm run test:coverage`，不要提交 git。
