## 2. 关键推理与取舍

- **为什么不拼装旧插件**：四个参考插件各自持有调度器、配置、凭据路径、状态文件与限流，且普遍把“已投递给 Agent/已发命令”当成“业务已完成”。外层开关无法统一这些语义，因此选择重写轻核心，把 Task/Operation/审批/幂等/额度/事件/outbox 收成一个唯一权威。
- **为什么不沉重**：核心只依赖 Node 22 与本地 JSON 账本；B 站协议、IM 宿主桥接、ffmpeg 生产 profile、商业 LLM/生图/TTS、ArtifactStore 全为可选适配器，禁用路径不 import 重 SDK、不 spawn、不轮询、不探测 ffmpeg/whoami，状态查询只读持久状态。remote/X/抖音以 `CAPABILITY_UNSUPPORTED` 明确拒绝。
- **为什么把灾备当最大遗漏（排除真实环境验证后）**：原方案已解决“已派发结果未知”（`unknown` 不重试）和“按计划停机搬迁”，但缺少主账本损坏、误删、介质丢失或迁移目标不可用时的可信恢复点与恢复后副作用防重放规则；不补齐时，所有幂等与额度保证会在非计划故障下失效。
- **灾备为何保持轻量**：复用既有 Store/Artifact/manifest/主体权限机制，用短暂 `checkpointFence` 取得一致恢复点，大媒体在事务外按固定引用复制；不引入消息中间件、共识服务、分布式租约、云 SDK 或远程接管。
- **灾备设计的三条硬规则**：正常迁移保持 `historyEpoch`，灾备恢复开新 epoch 并记录 `parent`；`kind=backup` 绝不等于迁移票据，恢复导入是只读且需证据驱动分 scope 解冻；保留集合按 tier 保底，最后有效 `full` 点不得被新增 `ledger` 点淘汰。
- **记忆为何仍只是规划**：记忆影响语气、选题与去重倾向，但不产生授权。若允许记忆替代人工审批或绕过额度/dryRun/迁移栅栏/恢复门禁，整个 fail-closed 模型失效。因此“事实＋偏好＋经验”的落地必须先经 GATE-MEM 审核并回写主规范，本轮只在 `TASKS.md` §9 写清机制、边界与验收场景，不占 FR/D/R 编号、不改账本 schema。
- **记忆连贯性的关键**：条目绑定 `workspaceId + 核验 accountId + historyEpoch + revision`，用 add/revise/supersede/tombstone 而非追加摘要；撤回记录必须跨备份恢复存活，否则旧恢复点会复活已撤销偏好与已遗忘内容。

## 4. 过程中发现并修正的真实缺陷

- 回滚旁路：SPEC 原允许“目标未激活即可从原快照恢复源端”，与 DESIGN“须以最新账本反向交接”冲突；已统一为 release 后一律先持久禁用目标与旧票据，再反向交接最新账本，取不到状态则保持阻塞。
- 派发上下文混淆：§21.2 曾要求所有副作用都携带 `OperationContext`；改为三类上下文（平台写/付费 `OperationContext`、免费本地阶段 `ExecutionDispatchContext`、通知 `OutboxDispatchContext`），共用闸门但不伪造 Operation。
- Manual 账本时点、`AccountRef/ContentRef` 平台无关化与 `platformData`、日记 `scopeKey` 路径、IM 四元去重键补 `botAccountId`、事件 payload 64KiB 上限、`journalPending` 10000 积压停新工作、unknown 优先于 failed 的结算聚合、`stageRequest` 补 `executionId`、FR-PRO-009 要求解码级媒体验证、outbox 与 Task 结算解耦、`parentTaskId/childTaskIds` 入表、ffmpeg 输入协议与网络 URL 注入面收窄。
- 灾备保留缺陷：最近/日/周并集可淘汰唯一有效 `full` 点；已补 per-tier 保底、prune 引用复查漏斗与对应验收行。
