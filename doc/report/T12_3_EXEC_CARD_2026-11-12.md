## 1. 执行前复核：两个已修 P1 与一个未决阻塞

### 1.1 F11（已修复）：全新目标在激活前无法建立首个恢复点

- 设计事实：`FR-MIG-007` 要求 activate 核对**目标侧**健康恢复点。`src/migration.js:929-938` 的 `_targetProtection()`、`src/backup-recovery.js:1172-1221` 的 `getProtection()` 要求：目标 dataDir 下存在 `backup-policy.json`；verification 的 `sourceRoot` 精确等于目标 dataDir、`independent=true`；目的地下有 **verified 且 policyRevision 匹配**的账本点，且未超 `maxPointAgeMinutes`（默认 20 分钟）。
- 缺陷：`backup create` 原先在 `migration.phase !== 'active'` 时一律拒绝（`src/backup-recovery.js:543-547/934-937`），而新目标从 import 到 activate 之间只能处于 imported/validated；于是**真实首迁目标永远无法满足激活前置**。离线测试长期用注入 protection fixture 通过（`test/migration.test.js` 旧用例），掩盖了该问题。
- 修复（2026-11-12）：仅当目标处于 imported/validated、本机 instance 为 paused/validated 且 `migrationId`/`previousInstanceId` 与目标迁移记录匹配时，允许本地 owner 通过受信 CLI 创建首个恢复点；源端 quiescing/sealed/released 仍拒绝；import 后保留空 `backups` 索引占位。回归用例：
  - `audit: an imported target can seed its first recovery point before activation`（真实 BackupService + 真实 activation，无注入）；
  - `audit: target bootstrap capture stays limited to imported or validated targets`。
- 对执行的影响：目标端 import 后，按 §4.4 先 `backup policy` 再 `backup create`，再 `validate/activate`。

### 1.2 F12（已修复）：CLI `migration import` 无 runtime 时崩溃

- 缺陷：CLI import 走独立入口（`cli.mjs:396-408`，`new MigrationService({ humanProof })`），但 `_importPackage` 调用 `_config()` 取包体上限时 `configService` 为 undefined → `TypeError: Cannot read properties of undefined (reading 'get')`，目标端 import 直接不可用。
- 修复：`_config()` 在无 configService 时返回文档默认上限（`maxFiles=100000`、`maxTotalBytes=68719476736`）；新增 `CLI migration import validates a sealed package without a running runtime` 回归（用真实 sealed 包 + 假 TTY verifier，断言 `phase=imported`、`backups={}`）。

## 5. 命令要点（相对 11-11 方案修正）

1. `migration export` / `migration validate` **不接受也不需要 `--confirm`**，但仍会要求 TTY 人类挑战（`migration activate/prepare/release/import/abort/reauthorize/backup policy/backup create` 需要 `--confirm`）。
2. `migration validate`、`migration activate` 必须显式 `--data-dir <目标目录>`；缺失时 CLI 返回 `CONFIG_INVALID` 用法错误（F13 修复前是 `path.resolve(undefined)` 的 `DEPENDENCY_UNAVAILABLE`）。`migration reauthorize` 同样必须显式传 `--data-dir`（否则会落到全局默认目录而非目标账本）。`prepare`/`export`/`release`/`abort`/`disable-target`/`rollback` 不再要求该参数（2026-11-15 修订）。
3. `migration import` 是独立入口（不打开生产 runtime），必须显式 `--from` 与 `--data-dir`，且目标目录必须不存在/为空。
4. `migration abort` 会删除 Windows 侧封存包目录（`packageDir`）→ **先传输/校验，再 abort**。
5. 目标端 import 后、activate 前，必须先放 `config.json` 并（完整路线）写 policy + 创建目标首个恢复点（F11）。
6. Windows 回迁把新账本导入**原名空目录**，使既有 `backup-policy.json` 的 `verification.sourceRoot` 继续精确匹配，避免再改 policy 与重建全部历史点。
7. WSL NAT IP 可能随 Windows 重启变化；`\\172.30.28.135\...` 失效时重跑 setup 脚本并检查 policy `destinationRoot`。
8. 迁移窗口内 DSH 关闭后，本 agent 不可用；所有 `--confirm` 挑战由 owner 本人输入，任何失败先保留输出，不重复真实写。

## 6. 失败处理与回滚

| 阶段/失败 | 处理 |
|---|---|
| release 前任一失败 | `migration abort <id> --confirm` → 源回到 active；包作废，不触碰业务事实 |
| release 后目标激活失败 | 源保持 retired；修复目标侧条件（policy/点/摘要）后按同 migrationId 重试 activate（幂等）；或按 §1.3 补目的地后重试 |
| release 后必须回 Windows | 把目标最新数据目录复制回 Windows → `migration disable-target <id> --target-data-dir <副本> --target-stopped --target-stop-evidence "<说明>" --confirm` → `migration rollback <id> --target-data-dir <副本> --to <新空目录> --confirm`。注意源端保护点 20 分钟超龄会令 rollback 的激活检查 `BACKUP_STALE`；计划内回迁优先走 A6-A7 正向迁移 |
| 灾难级 | Phase 0 文件系统副本或独立故障域 protected 点走 `recovery restore --from ... --to <新空目录> --confirm`（只读新 epoch，不自动恢复写权限） |
